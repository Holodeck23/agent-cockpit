## Enforcement design gate

The existing runner converts observed hook failures to a native blocking answer. Its shell tail handles ordinary runner launch/crash exit statuses. Its timeout margin makes an internal timeout answer more likely to arrive before the native timeout. These mechanisms do not establish that the native caller blocks if the shell/runner cannot return an answer, the native hook engine times out, or native parsing/serialization fails.

Read-only recheck of the preserved Codex source at `9e8562b` confirms the mismatch: `hooks/src/events/pre_tool_use.rs` initializes `should_block` false and retains it for execution errors, malformed output, unsupported decisions, ordinary nonzero exits, an exit-2 answer without a reason, and serialization failure. Existing native tests explicitly retain several of these cases as failing open. `core/src/hook_runtime.rs` returns Continue when `should_block` is false, and also when a blocking reason is missing. This is source evidence, not a new live protected-effect reproduction, and it does not identify the bytes of every selectable Codex executable.

Production app-server hook notifications are observations; reacting after a failure notification is not a demonstrated pre-action gate. Current command/file approvals and host bridge grants also do not establish interception of every native tool call. For Claude, the wrapper source itself documents the native nonblocking timeout/error distinction. The earlier packaged failure tests exercise errors inside a functioning wrapper, with narrower scope than the full promise.

The next enforcement design must meet this finite contract before broad production integration:

1. Name every protected operation and the native point that waits before its effect. Cover commands, file changes, reads and connector calls where a selected policy applies. Preserve the complete expected policy inventory; a missing/untrusted expected hook cannot silently mean no policy.
2. Require a current authenticated host allowance bound to operation identity, arguments, provider/session/turn, account/workspace, manifest and authorization generation. No allowance, timeout, malformed answer, missing runner or stale binding must deny at that native waiting point.
3. Evaluate reviewed host-owned policy roles before returning the allowance. Bind the dependency bundle and all completion checks to one persisted batch, rather than counting per-handler IDs or assistant text.
4. Fence dispatch, approvals and grants immediately on explicit Stop/revocation. A late allowance or result cannot remove the fence. Persist completion/Stop decisions and recovery without restarting correction budgets or deadlines after a crash.
5. Demonstrate each failure before a synthetic protected effect, including loss of the outer runner/response and delayed effects. Pair each denial with a successful control. Test without automatic subagents, real credential relocation, installed-app changes or adoption of the experimental provider.

First evaluate a documented supported all-action callback/permission interface against that contract. **Stop that route if any protected action can proceed without its required allowance.** Another supervised wrapper around the same failing-open hook path does not resolve it. If the supported interface cannot meet the contract, present the smallest provider-boundary change and its maintenance/adoption requirements for an explicit scope decision; do not begin a provider rewrite. The previously proposed compatibility contract is a separate human decision, not the fallback result of this design test.

## Supported-interface audit result

The bounded read-only audit found a concrete counterexample in preserved Codex source `9e8562b`. `core/src/tools/registry.rs` awaits PreToolUse hooks, but a Continue result proceeds to `handle_any_tool`. `core/src/tools/handlers/mcp_resource/read_mcp_resource.rs` then executes native `mcp.read_resource` through `run_resource_operation`; that operation emits activity and awaits the read, without requesting a host allowance. Combined with the verified hook-error Continue branch, this path can perform a policy-protected resource read without the proposed host permission gate. This is a source trace, not a newly executed exploit or an assertion about every future native version.

The inspected app-server request schema supplies command/file approvals, additional-permission requests, MCP elicitation and client-executed dynamic tools. Its `item/tool/call` request executes a registered dynamic tool; it does not intercept every native built-in operation. `AskForApproval` governs command approval conditions; its granular fields do not create an all-tool host policy callback. Replacing native operations with client tools would be a different adapter/compatibility design, not qualification of the existing native path.

The hash-pinned Claude executable's metadata-only help declares permission modes but neither `--permission-prompts` nor `--permission-prompt-tool`. Cockpit already supports hidden stdio approval behavior. Absence from help does not prove absence of a hidden interface, and no stronger Claude failure-containment claim follows. No additional model, account or tool-effect probe was needed after the Codex counterexample met this route's stop condition.

**Result: the current supported-interface route cannot qualify the full contract.** Broad production wiring remains held. More wrapper/permission-option experiments on this same route are not the next task.

## Concrete scope decision prepared for the human

To retain full W13, a separately authorized native-boundary feasibility unit would have to provide an opt-in, expected-policy-aware gate before protected native tool effects. First evaluate the smallest core/configuration change: retain an expected reviewed policy manifest, deny policy/unknown hook execution or parsing failures and missing blocking reasons before handler execution, and refuse missing/untrusted expected policy sources. A new host callback protocol is a possible design, not an assumed requirement. Any implementation must (a) prevent expected policies disappearing through trust/discovery failure, (b) finish the required current policy decision before effects, (c) deny outer-runner/response failure and stale identity, and (d) cover built-in, resource/connector and non-function operations instead of only dynamic tools. Existing native behavior outside the opt-in contract must retain its own compatibility tests. Use synthetic effects, retain every failure, preserve the current memory extension and require a fresh source/runtime identity. No adoption, installation or release follows from a spike. Claude still needs a supported qualifying mechanism; a Codex-only patch cannot close W13.

This requires provider-boundary work beyond the current no-provider-rewrite boundary. It has not been authorized or started. The alternative is explicit approval of the already prepared compatibility-pilot contract in the canonical vault direction review/delivery plan, followed by its row-by-row authority reconciliation and safe-startup design. That proposal changes acceptance requirements; choosing neither leaves the full contract blocked. The source audit itself does not choose for the human or waive an acceptance row.
